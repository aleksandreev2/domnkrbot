# Telegram-заявки на перевод — дизайн

Дата: 2026-09-07
Статус: утверждено пользователем для дальнейшего технического планирования
Репозиторий: `aleksandreev2/domnkrbot`

## 1. Цель

Добавить в существующий Telegram-бот «Дом Некроманта» удобный текстовый сценарий, через который пользователи смогут предлагать новеллы на перевод прямо в личном чате с ботом, без обязательного перехода на сайт.

Основное разветвление сценария:

1. новелла уже есть на RanobeLib;
2. новеллы нет на RanobeLib.

Новый поток должен использовать уже существующие Telegram inline-кнопки, текущую D1-базу, существующие сущности заявок и текущую web-админку. Сайт и существующие подписки на новые главы не должны ломаться.

## 2. Основные UX-принципы

- Telegram — основной интерфейс подачи заявки.
- Минимум обязательных полей.
- Обычный текст пользователь вводит только там, где это действительно необходимо.
- Все выборы, где возможно, делаются inline-кнопками.
- Не превращать подачу заявки в длинную анкету.
- Сценарий должен занимать примерно 3–5 пользовательских действий.
- На каждом этапе должны быть понятные кнопки «Назад» и/или «Отмена», где это уместно.
- Перед созданием новой записи необходимо проверять дубликаты.
- После отправки пользователь должен видеть статус и иметь возможность открыть список своих заявок.

## 3. Главное меню Telegram-бота

`/start` должен открывать нормальное главное меню, а не сразу уводить пользователя только в подписки.

Предлагаемый вид:

**☠️ Дом Некроманта**

Что хотите сделать?

- `📚 Предложить новеллу`
- `🔔 Уведомления`
- `🗂 Мои заявки`
- `🌐 Сайт`

Поведение команд:

- `/start` → главное меню;
- `/propose` → сразу открыть сценарий предложения новеллы;
- `/subscriptions` → оставить существующий сценарий подписок;
- `/notifications` → оставить существующий центр уведомлений;
- `/site` → существующая ссылка на сайт;
- `/help` → краткая справка по возможностям бота.

## 4. Сценарий «Предложить новеллу»

Первый экран:

**Есть ли эта новелла на RanobeLib?**

Кнопки:

- `✅ Есть на RanobeLib`
- `❌ Нет на RanobeLib`
- `↩️ Назад`

## 5. Ветка «Есть на RanobeLib»

### 5.1. Поиск тайтла

Бот просит:

**Пришли ссылку на карточку RanobeLib или напиши название.**

Поддерживаются два пути:

1. пользователь присылает URL RanobeLib;
2. пользователь вводит название.

Если введено название, бот ищет по локальному синхронизированному RanobeLib-каталогу и показывает до нескольких наиболее подходящих вариантов.

Пример:

- `[Я стал гениальным маглом…]`
- `[Второй похожий тайтл]`
- `[Третий похожий тайтл]`
- `[🔎 Ничего из этого]`

После выбора бот показывает подтверждение:

**Я нашёл:**

- название;
- количество глав;
- последнюю доступную главу;
- при наличии — команду перевода;
- при наличии — статус перевода;
- состояние иммунитета/защиты, если его можно определить надёжно.

Кнопки:

- `✅ Да, это он`
- `🔄 Выбрать другой`
- `❌ Отмена`

### 5.2. RAW

После подтверждения тайтла бот просит именно файл, а не ссылку:

**Если есть RAW — отправь файл.**

Кнопка:

- `Пропустить`

RAW — файл, например EPUB/TXT/ZIP или другой поддерживаемый формат.

Важно: для этого сценария нельзя подменять RAW-файл требованием прислать ссылку на RAW.

Должен использоваться существующий R2/RAW-upload подход проекта там, где это возможно, с адаптацией под Telegram file flow.

### 5.3. Комментарий

Бот спрашивает:

**Хочешь что-нибудь добавить?**

Кнопка:

- `Без комментария`

Комментарий необязателен.

### 5.4. Финальное подтверждение

Перед созданием заявки бот показывает сводку:

**Проверь заявку**

- RanobeLib: ✅ есть
- Тайтл: …
- RAW: приложен / нет
- Комментарий: …
- Иммунитет: значение или безопасный статус неопределённости

Кнопки:

- `📨 Отправить`
- `✏️ Изменить`
- `❌ Отмена`

## 6. Ветка «Нет на RanobeLib»

Сценарий должен быть коротким.

Минимум:

1. название новеллы;
2. ссылка на страницу оригинала / официальный источник произведения;
3. RAW-файл — необязательно;
4. комментарий — необязательно;
5. финальное подтверждение.

Не требовать от пользователя вручную заполнять автора, жанры, описание, язык и прочую расширенную анкету, если это не нужно для самого решения о переводе.

Перед отправкой бот может отдельно предупредить, что карточка RanobeLib не найдена, и предложить подтвердить это состояние.

## 7. Проверка дубликатов

Перед созданием новой заявки бот обязан искать существующие активные заявки на тот же тайтл.

Если дубликат найден, новую запись не создавать автоматически.

Показать пользователю:

**Этот тайтл уже предлагали. Сейчас у заявки N голосов.**

Кнопки:

- `👍 Поддержать заявку`
- `👁 Посмотреть`
- `↩️ Назад`

Для тайтлов с RanobeLib предпочтительно связывать дубликаты по стабильному идентификатору RanobeLib (`book_ref` / `ranobelib_id`), а не только по текстовому названию.

Для тайтлов без RanobeLib использовать нормализованное название и при возможности оригинальный URL/идентификатор источника.

## 8. «Мои заявки»

В главном меню должен появиться раздел `🗂 Мои заявки`.

Он показывает последние заявки пользователя с текущими статусами.

Пример:

- 🟡 Название A — На рассмотрении · 18 голосов
- 🔵 Название B — В плане
- 🟢 Название C — Перевод начат

При открытии одной заявки показывать:

- название;
- RanobeLib / без RanobeLib;
- текущий статус;
- количество голосов;
- дату подачи;
- комментарий пользователя;
- комментарий администратора, если он предназначен пользователю;
- приложенный RAW, если применимо;
- ссылку на RanobeLib, если применимо.

## 9. Уведомления о статусе заявки

При изменении значимого статуса пользователь должен получать Telegram-уведомление.

Пример:

**📚 Статус заявки изменился**

«Название» → **В плане**

Для отклонённой заявки при наличии пользовательского admin note показать причину/комментарий.

Уведомления нужны как минимум для переходов в:

- approved;
- planned;
- in_progress;
- done;
- rejected.

## 10. Иммунитет RanobeLib

### 10.1. Что известно

Публичный API RanobeLib отдаёт полезные данные по тайтлу и главам, включая:

- `teams`;
- статус перевода (`scanlateStatus` при запросе соответствующего поля);
- список глав;
- данные веток глав;
- `created_at`;
- команды веток;
- некоторые дополнительные поля вроде `expired_type` / `expired_at` на уровне главы.

На момент фиксации ТЗ надёжного публичного поля вида `has_immunity`, `protected_until` или эквивалента не подтверждено.

Нельзя интерпретировать `expired_at` или похожее поле как иммунитет без дополнительной проверки.

### 10.2. Требуемое поведение

Если точный иммунитет можно получить из подтверждённого API/внутреннего запроса RanobeLib:

- показывать точное состояние;
- при наличии даты показывать дату окончания.

Пример:

`🛡 Иммунитет до 18 сентября 2026`

Если точного источника нет, бот не должен придумывать значение.

Показывать:

`⚪ Иммунитет: не удалось определить автоматически`

Допустимо добавить вычисляемый эвристический статус только в админке, и только с явной маркировкой:

- `🟢 предположительно действует`;
- `🔴 предположительно истёк`;
- `⚪ недостаточно данных`.

Эвристика должна сопровождаться основаниями, например:

- активная команда;
- дата последней главы команды;
- статус перевода.

Эвристический результат нельзя выдавать пользователю как точный факт.

## 11. Админка — общий UX

Существующий раздел `Заявки` сохранить, но переработать в очередь модерации.

Верхняя часть:

- `Новые`;
- `Одобрено`;
- `В плане`;
- `В работе`;
- `Закрытые`.

Дополнительные фильтры:

- `Все`;
- `✅ Есть RanobeLib`;
- `❌ Нет RanobeLib`;
- поиск по названию.

Карточки в списке должны быть компактными. Не показывать сразу все административные действия на каждой карточке.

## 12. Админка — карточка заявки

### 12.1. Если тайтл есть на RanobeLib

Показывать:

- обложку;
- название;
- прямую ссылку;
- `book_ref` / `ranobelib_id`;
- количество глав;
- последнюю главу;
- команду/команды перевода;
- статус перевода;
- иммунитет или безопасный статус его неопределённости;
- автора заявки;
- дату заявки;
- пользовательский комментарий;
- RAW-файл;
- количество голосов.

### 12.2. Если тайтла нет на RanobeLib

Показывать:

- название;
- оригинальное название, если есть;
- URL оригинального источника;
- пользователя;
- дату;
- комментарий;
- RAW;
- голоса.

## 13. Админские действия

В детальной карточке:

- `✅ Одобрить`
- `📌 В план`
- `🚧 В работу`
- `✅ Готово`
- `❌ Отклонить`

Отдельное поле:

**Комментарий пользователю**

Существующий `admin_note` можно переиспользовать или разделить на внутреннюю и пользовательскую заметку, если при техническом проектировании выяснится, что админам нужен приватный комментарий.

## 14. Проверка RanobeLib для заявок «нет на RanobeLib»

В админке должна быть кнопка:

`🔎 Проверить RanobeLib`

Она ищет похожие тайтлы.

Если найден вероятный матч:

**Похоже, карточка уже существует:**

«Название…»

Кнопка:

- `🔗 Связать с этой карточкой`

После связывания заявка должна перейти из режима `без RanobeLib` в связанную RanobeLib-заявку без пересоздания заявки и без потери голосов, автора, RAW или истории статусов.

## 15. Данные и модель

При техническом проектировании предпочтительно расширить существующую модель, а не создавать параллельную систему заявок.

Требуется предусмотреть как минимум:

- признак/тип источника: RanobeLib или external;
- стабильную связь с `ranobelib_titles`;
- возможность хранить RAW attachment;
- сохранение текущих статусов;
- дедупликацию;
- хранение Telegram conversation state;
- историю значимых смен статуса или достаточную основу для уведомлений;
- возможность безопасно уведомлять пользователя после админского действия.

## 16. Telegram conversation state

Новый wizard требует серверного состояния диалога.

Нельзя полагаться только на текст предыдущих Telegram-сообщений.

Состояние должно хранить как минимум:

- user_telegram_id;
- текущий шаг;
- выбранную ветку (`ranobelib` / `external`);
- выбранный RanobeLib title id/ref;
- введённое название;
- URL источника при external flow;
- Telegram file metadata / raw upload reference;
- комментарий;
- timestamp обновления.

Состояние должно иметь TTL/механизм очистки незавершённых диалогов.

`/start`, `/propose` и `Отмена` должны предсказуемо сбрасывать или заменять незавершённое состояние.

## 17. Совместимость

Нельзя ломать:

- существующие подписки;
- `/subscriptions`;
- `/notifications`;
- текущие webhook security checks;
- Telegram Login сайта;
- web-заявки;
- публикационный workflow;
- RanobeLib sync;
- существующие D1 данные.

Изменения схемы D1 выполнять отдельной forward-only migration.

## 18. Ошибки и fallback

- Если RanobeLib API недоступен, пользователь должен получить понятное сообщение и возможность повторить поиск.
- Если локальный snapshot доступен, использовать его как fallback там, где это разумно.
- Если RAW-файл слишком большой или неподдерживаемый, объяснить ограничение до финальной отправки заявки.
- Если Telegram file download временно не удался, не терять весь wizard state.
- Если пользователь отправил неожиданный текст на шаге с кнопками, бот должен повторить ожидаемое действие, а не молча игнорировать сообщение.
- Повторные callback/update события Telegram должны обрабатываться идемпотентно настолько, насколько это возможно.

## 19. Критерии готовности

Фича считается готовой, когда:

1. Пользователь может полностью подать заявку в Telegram без сайта.
2. Работают обе ветки: RanobeLib и без RanobeLib.
3. Для RanobeLib можно выбрать существующий тайтл через URL или поиск по названию.
4. RAW принимается именно как файл и может быть пропущен.
5. Дубликаты не создают мусорные копии заявок.
6. Пользователь видит свои заявки.
7. Пользователь получает уведомления о значимых сменах статуса.
8. Админка умеет фильтровать и подробно просматривать оба типа заявок.
9. Админ может связать external-заявку с найденной карточкой RanobeLib.
10. Иммунитет никогда не показывается как точный, если источник не подтверждён.
11. Существующие подписки, сайт, публикации и синхронизация продолжают работать.
12. Есть тесты на wizard state, callbacks, дедупликацию, создание заявки, статусные уведомления и основные admin API.

## 20. Вне текущего scope

Не включать без отдельного решения:

- автоматическое принятие решения о переводе;
- обязательный AI-анализ предложенной новеллы;
- автоматическую загрузку карточки на RanobeLib;
- автоматический перевод RAW;
- сложную систему рейтингов пользователей;
- публичное ранжирование пользователей;
- обязательный сбор жанров/авторов/описания руками пользователя.
